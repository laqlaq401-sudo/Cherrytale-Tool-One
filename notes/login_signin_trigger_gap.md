# 登录签到钩子「从未执行」的根因排查（2026-10-17）

> 对象：`tasks/login_signin.py` —— 登录后自动发 33055 结算「每日签到 + 活动登入奖励」的内置钩子。
> 背景：实现时（2026-10-06）真机验证成功；但实际日常使用中用户发现它**根本没有执行**。
> 本文只排查、未改任何代码。

## 结论（一句话）

**不是执行失败，而是没有任何一天会走到"执行"那一步**：钩子只挂在「登录动作」上，
而工具的现实日常里**只有"首次登录 / 令牌失效重登"那天才有登录动作**——
会话持久化后，每天打开工具都是从首页（index.html）直进任务界面，
**登录页根本不会被打开**，钩子永远没有触发时机。

「不写前端卡片、登录后静默执行」这个设计本身没错，错的是：**省掉卡片的同时，
没有补一个"每天必然发生"的触发点**——唯一的触发被挂在了"登录"这个非日常事件上。

## 证据链（逐条已核）

1. **钩子的全部调用点只有两处**（全仓库 `grep run_if_first_login_today`）：
   - `tasks/login.py:474` —— 真实登录任务执行到"会话就绪"之后（plan_only 早退不触发）；
   - `webapi/app.py:640` —— `/api/login/enter` 的**直连分支**里、令牌探活成功之后。
2. **`/api/login/enter` 只有登录页会调**（`grep "login/enter" web/` 全仓库仅两处命中，都在 `login.js`）：
   - `login.js:331` `doDirectEnterZone`（点已保存的区服卡"一键直达"）；
   - `login.js:480` `doEnterServer`（选完区点"进入游戏"）。
   ⇒ **只有用户在 login.html 上操作时，才可能触发钩子。**
3. **登录页只在"没有会话"时才会出现**：
   - 应用入口恒为 `/` → 服务器根路由返回 **index.html**（`webapi/app.py:1559`：`relative = path.lstrip("/") or "index.html"`）；
   - index 启动时问 `/api/health`，`next_screen = has_session ? "main" : "login"`（`webapi/app.py:420`）；
   - `has_session` 只表示"会话文件里解析得到一份会话状态"，**不探活、不看令牌是否过期**
     （`services/runner.py:406-467`；只读，不产生任何网络请求）；
   - 安卓 WebView 入口 `http://127.0.0.1:端口/`（`MainActivity.kt:26`），PC 壳同理——两端都从 "/" 进。
4. **任务界面的"启动"自动批不会捎带登录**：
   - `runAutomation("启动")`（`app.js:318`）只提交 auto 组**非 hidden 且已勾选**的任务；
   - `collectTasks` 明确跳过 hidden（`app.js:2831`：`if (!task.enabled || task.hidden) continue`）；
   - `login` 任务 `hidden=True`（`services/task_spec.py:816-823`，"由专用界面负责"）⇒ 永远不在自动批里；
   - 且钩子是登录任务的 **Python 副作用**，不是一个独立任务，任何批次都不会"捎带"到它。
5. **记账文件的实证**：`.login_signin_state.json` 全部记录如下（各运行目录数据一致）：
   - `10-06 05:01`（#167 主号，实现/验证日）、`10-16 20:11`（#167，开发会话）、`10-16 21:50`（#98 空桉，打包版测试）；
   - **10-07 ~ 10-15 的日常使用期零记录** —— 与"日常不经过登录页"完全吻合。

## 为什么当初的验证没暴露它

- 验证场景必然包含"登录"（要进游戏才能测）：两条调用路径都会被走到 → 每次验证都成功；
- 原设计（`recon_findings.md` §23.5）以为直连分支覆盖了"令牌活着跳过登录的日子"——
  但直连分支的前提是**用户还在登录页点卡片**（direct=true）；
  真实的"令牌活着"日常是**首页直进、根本不出现登录页**——这两个场景被混淆了。

## 修复方向（未实施，待拍板）

原则不变：无卡片、无开关、静默、每自然日一次、失败不影响主流程、33055 幂等。
- **A（推荐）服务端**：把"每自然日一次的 33055"挂到"当天第一次真正开始执行批次"的时刻
  （runner 侧，如 run 准备阶段/首个任务执行前）。覆盖 PC EXE / 安卓 / CLI 三端、无需前端改动、
  无需重打 APK。需设计：仅在有会话的有效运行上触发、dry-run 策略、失败静默、幂等记账沿用
  `.login_signin_state.json`、不与主流程阻塞耦合。
- **B 前端**：index boot 的"启动"时刻显式调一个专用端点（如 `POST /api/login_signin/touch`）。
  效果同 A，但要改前端 + 同步安卓 + 重打 APK。
- **C 任务化**：并入 once_per_day 那批"开机动作"——与当初"不要卡片、不要开关"的决策冲突，不优先。

→ **方案已定稿（方向 A，2026-10-17）：见 `notes/login_signin_run_trigger_plan.md`**

## 排查中顺带确认的两件事（非 bug）

- `login` 任务虽 `group="auto"`，但 `hidden=True` 使它永远不进任何前端批次——这是
  "登录/换号由专用界面负责"的刻意设计；
- `.login_signin_state.json` 与日常（05:00）、宴席（06:10）各自独立记账，键为 `s={server}|p={player}`。
