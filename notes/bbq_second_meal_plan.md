## 一、（★已作废 · 见 §六）先接受你的更正：不存在"补吃"

你的更正把整套问题重新定性了：

- 游戏以**天**为刷新单位，**过了刷新点，前一天的宴席状态全部重置**；
- 所以不存在"在第二顿时间里补吃第一顿"这种跨顿补偿 ——
  **两顿各自独立、各自在自己的窗口内有效、各自在窗口结束后作废**。

因此正确的模型不是"补救"，而是**两顿各自独立处理**：

| | 窗口 | 窗口内可做 | 窗口结束后 |
|---|---|---|---|
| **早宴席**（第一顿，`weeks==0`，501000004） | 06:10–13:59 | 免费吃 / 付费邀请 | **本顿作废**（不可再发） |
| **晚宴席**（第二顿，`weeks==2`，501000005） | 14:00–次日06:00 | 免费吃 / 付费邀请 | **本顿作废**（不可再发） |

> 这比第四版简单得多，也**更符合你的 UI 直觉**：每一顿就是一个"在它的时间里点它"的按钮。

## 二、你的新设计（我完全同意，且认为优于"一个按钮自动判断"）

### 2.1 你的方案原文要点

1. **一个包 → 一个按钮**：两顿 = 左右两个按钮；
2. 按钮名不叫"执行"，叫 **「早宴席」/「晚宴席」**；
3. **吃过就灰掉**，不再往服务器发多余包；
4. **两个邀请开关**，各自独立；
5. **在某一顿的时间之外，那一顿的邀请开关默认不邀请**（与开关本身状态无关 ——
   即"时间不合法时，即使开关开着也强制不邀请"）。

### 2.2 我为什么同意

**"一个按钮自动判断"确实承载不了你要的语义。** 它必须自己决定：
现在几点、该发哪个包、第一顿吃没吃、要不要顺带补 —— 这些**互相独立的意图被塞进一次点击**，
用户既看不清也控不住。而"一个包一个按钮"把**协议与界面一一对应**：

| 你的按钮 | 发出的包 | 时间合法区间 | 邀请开关 |
|---|---|---|---|
| 早宴席 | `15003{501000004, 好友列表}` | 06:10–13:59 内可点 | 独立开关 |
| 晚宴席 | `15003{501000005, 好友列表}` | 14:00–06:00 内可点 | 独立开关 |

这正是抓包里两条 `15003`（`501000004` / `501000005`）的真实映射，**一眼可对**。

### 2.3 我认为可以再完善的三处

#### 完善点 A：**"灰掉"需要区分三种不同的灰**（重要）

「吃过就灰」只说了其中一种。实际有三种互斥的置灰原因，**界面上要能区分**，
否则用户看到灰按钮不知道是"吃过了"还是"没到时间"还是"过期了"：

| 状态 | 触发条件 | 建议文案 | 可点 |
|---|---|---|---|
| 未到时间 | `now < startDateTime` | 「未开始 · 14:00 开放」 | ❌ |
| 可执行 | `start ≤ now ≤ end` 且未吃过 | 「早宴席」 | ✅ |
| 已吃过 | 本游戏日该顿已成功执行 | 「已运行」 | ❌ |
| 已过期 | `now > endDateTime` | 「本顿已结束」 | ❌ |

> ⚠️ 你说的"吃过就灰"我完全同意；但**若不区分 "未到时间" 与 "已过期"**，
> 用户在早上看到晚宴席是灰的，会以为"今天晚宴席废了"。
> 这两个状态的**处置其实相同（都不可点）**，但**文案必须不同**。

#### 完善点 B：**"吃过了"的状态由谁记、哪天算"今天"** —— 这是最容易出错的地方

服务端**不提供**"这顿吃没吃"（抓包实证：32008 无任何状态字段）。
所以"吃过就灰"必须由本工具记录。这里有三个必须定的细节：

1. **存在哪？** → **✅ 已定：放后端**（用户 2026-10-05 拍板）。
   实现要点：**不复用 `auto_done`**（那是"自动任务今日已跑"的清单，语义不同、且换日口径不同），
   而是**给宴席单开一份后端记录**，随 `/api/tasks` 一起下发给前端（新增一个字段，
   例如 `bbq_done: {morning: true, evening: false}`），前端据此置灰。
   记录键仍按 **`identity_key`（角色 + 区服）** 隔离，避免换号串台。
2. **哪天算"今天"？** → **✅ 已定：宴席自己的换日点 = 晚宴席结束时间（次日 06:00），
   与游戏日（05:00）独立**（用户 2026-10-05 拍板）。
   - 实现：宴席日 = "**晚宴席 endDateTime 之后的第一个时刻起算**"的日期；
     简单地说，**早宴席 + 晚宴席这"一整天"归同一个宴席日**。
   - 具体判据（推荐）：以**早宴席的日期**为该宴席日的标识 ——
     即 `date(早宴席.startDateTime)` 作为这一天的 key。早 06:10 与当晚 14:00–次日06:00
     都落在同一个 key 下；到了次日 06:00 之后，服务端会下发**新的一天**的期
     （新的 groupID 或新的 startDateTime），key 自然变化 → 记录自动作废。
   - ⚠️ **不要用游戏日 05:00**：晚宴席在 05:00–06:00 这一小时里若按游戏日切换，
     会刚吃完就被判成"新的一天"而重置，允许重复发包。这正是你要求"独立开"的原因。
   - ⚠️ **落地前需确认一件事**：服务端下发的"新一天"是哪一天 ——
     抓包只有 10-02/10-03 两天，**是否每天/每期都重新下发新 startDateTime 未验证**。
     若服务端在一期内固定下发同一组时间戳，则不能靠 startDateTime 区分天，
     需要改用**本机日期 + 06:00 边界**来算宴席日（实现时二选一，先按后者更稳）。
3. **"吃过"以什么为准？** → 以 **`15004.errorCode == 0` 的成功响应**为准
   （服务端认定成功才置灰、才记账）；被拒绝（非 0 码）**不置灰、不记账**，允许重试。

#### 完善点 C：**邀请开关"时间外强制不邀请"要落在哪一层**

你说"第一顿时间之外，第一个邀请开关默认不邀请"（第四版已更正为：**每一顿在它自己的
窗口之外都强制不邀请**）。这里要定**"强制"发生在哪一层**：

- **纯前端**（界面把开关灰掉）：用户可以绕过（改 local storage / 直接调 API）→ 不够；
- **后端闸门**（组包前判断"该期窗口是否覆盖 now"，不覆盖就强制走免费档，
  并在日志里明说"窗口外，已忽略邀请开关"）：**这才是真正的强制**，
  与项目"消费闸门必须在组包前"的一贯原则一致（`request_diamond_spend` 的位置要求）。

> ⇒ **✅ 已定（用户拍板）：前端置灰 + 后端强制，双保险。** 前端负责"看得懂"，后端负责"拦得住"。

### 3.2 后端行为（尽量少动既有分支）

```
早宴席按钮 → 任务参数 {meal: "morning"}
晚宴席按钮 → 任务参数 {meal: "evening"}

execute():
  拉 32008（不变）
  ├─ 无 meal 参数（CLI 老用法 / 兼容）→ 保持现状三分支不变 ← 关键：不影响已跑通功能
  └─ 有 meal 参数 →
       定位该顿的期（morning→weeks==0；evening→weeks==2）
       ├─ 窗口不覆盖 now → 拒绝并说明（不猜、不发）
       ├─ 邀请开关开 且 窗口覆盖 now → 走现有邀请分支（**复用 `_invite_and_eat`**）
       └─ 否则 → 走现有免费分支（**复用 `_eat_free`**，只是 groupID 由 meal 指定）
```

**关键设计**：**既有 `execute()` 在"没有 meal 参数"时行为完全不变** ——
CLI、旧调用方、已跑通的路径都不受影响；新参数只是多了一条"指定顿"的入口。

**后端"窗口外强制不邀请"落在哪**（已定）：
定位到该顿的期后，若 `not (start ≤ now ≤ end)` → **不发包，直接返回"本顿未开放/已结束"**；
若窗口覆盖 now 但缺少邀请授权 → 走免费档；邀请授权与窗口都满足 → 走邀请分支。
即：**"窗不覆盖" 优先于 "开关开着"**，开关无权让一个过期的期发邀请。

### 3.2.1 后端记录的写入点（新增）

`15004.errorCode == 0` 成功之后，写一条：
`{宴席日 key, player+server, morning: true / evening: true, at: 本机时间}`。
`/api/tasks` 响应里带上它（新增字段，**不改 `auto_done` 的语义**）。
换日（宴席日 key 变化）时旧记录自然作废 —— 与 `daily_state` 的"跨日自动作废"同一手法。

### 剩下一处需要你在实现前提早留意（不是要你现在定，是提醒风险）

**无法确认服务端是否每天重新下发一组新的 `startDateTime`**。

- **吃过就灰**：✅ 同意；且必须**区分"未到时间/已过期/已吃过"三种灰**；
  "吃过了"由**后端记账**（服务端不给状态），换日按**晚宴席结束（次日 06:00）**算，
  **与游戏日 05:00 独立**。
- **不影响既有功能**：新设计走"新增 `meal` 入口"，**无 `meal` 参数时老路径逐字节不变**。

**四项决定已全部拍板，本方案可以进入实现阶段。**

# 六、第七版：补吃成立 + 宴席日 06:10 修正（2026-10-06 · 待批 · 未写代码）

## 6.1 现状为什么是错的

`tasks/bbq.py::_execute_meal` 现在的判定链是：

```
_window_state(interval, now_ms)
  ├─ not_started / ended  → 返回 meal_window_closed，一个 15003 都不发
  └─ covering             → 才继续（已吃检查 → 邀请/免费）
```

于是早宴席一过 13:59 就被判 `ended`：**前端**四态落到 `expired` → 按钮 disabled（"黑掉"）；
**后端**即使能点也会被 `meal_window_closed` 拦成零发包。

实际上「吃」这件事本来就不该被该顿窗口拦住 —— **窗口只管「邀请」**。

## 6.2 抓包实证（2026-10-03 凌晨 · +08:00）

两份 saz 的 `32008` 都下发同一对期（`weeks` 字段 = 0 / 2）：

| weeks | groupID | 服务端下发窗口 |
|---|---|---|
| 0 | `501000004`（早宴席） | 10-03 06:10 → 13:59 |
| 2 | `501000005`（晚宴席） | 10-02 14:00 → 10-03 06:00 |

实际发出的 `15003`：

| 抓包 | 时刻 | 请求 | 响应 |
|---|---|---|---|
| `过时间无法用钻石邀请的宴席.saz` | 00:39 | `15003{501000004, 无好友}` | **errorCode=0** |
| `免费+付费宴席.saz` | 00:42 | `15003{501000005, 4 好友}` | errorCode=0 |
| 同上 | 00:42 | `15003{501000004, 无好友}` | **errorCode=0** |

两条结论：

1. **早宴席在窗口外照发照收**（服务端认）。该份包名"过时间无法用钻石邀请"正说明：过点之后
   **只剩"免费吃"这一条路**，付费邀请那条没有了 —— 那份 saz 里确实**一条付费邀请包都没有**；
2. 两次吃早宴席时，它的窗口（06:10–13:59）**从未覆盖当下** —— 说明**吃的合法期 ≠ 该期窗口**。

> **为什么"窗口外也能吃"**：因为**宴席日**不是"该期窗口那一段"，而是 **06:10 刷新 → 次日 06:10**。
> 06:10 刷新当天的**第一顿**（早宴席，窗口 06:10–13:59）；14:00 起是**第二顿**
> （晚宴席，窗口 14:00–次日 06:00）；次日 **06:00–06:10 是空档期**（第二顿已结束、第一顿未刷新）。
> 所以 00:39 属于"前一宴席日的收尾"，此时点早宴席 = **补吃**（本顿邀请窗口早已过，故不可邀请）。

## 6.3 三套"日"互不相同（本次只动宴席日）

| 口径 | 边界 | 谁在用 |
|---|---|---|
| 游戏日 | **05:00** | 日常刷新（`config.DAILY_RESET_HOUR`） |
| 日常 / 活动日 | 各自定义 | 签到、活动等 |
| **宴席日** | **06:10** | 早/晚两顿的归属 + "已吃"记账（`models.daily_reset.banquet_day`） |

⚠️ 现实现是 `models/daily_reset.BANQUET_RESET_HOUR = 6`（**06:00 整点**），按第七版口径应改成
**06:10** —— 也就是要在"小时"之外加**分钟**粒度。06:00–06:10 仍算**前一宴席日的尾巴**（此时两顿都不可吃）。

## 6.4 第七版规则（最终口径）

**早宴席（`501000004` / `weeks==0`）**

| 时段 | 能吃吗 | 能邀请吗 |
|---|---|---|
| 06:10–13:59（自己窗口） | ✅ 吃 | ✅ 能（开关生效） |
| 14:00–次日 06:00 | ✅ **补吃** | ❌ **强制不邀请** |
| 06:00–06:10（空档） | ❌ **不发包** | ❌ |

- **可吃判据**：**不看时间**，只看「本宴席日是否已吃过」（+ 空档期不发包）。
- **可邀请判据**：`start ≤ now ≤ end`（该期自己的窗口）；窗口外**后端强制忽略邀请开关**。

**晚宴席（`501000005` / `weeks==2`）—— 不放宽，维持现状**

| 时段 | 能吃吗 | 能邀请吗 |
|---|---|---|
| 14:00–次日 06:00 | ✅ | ✅ |
| 其它（含空档） | ❌ **不发包** | ❌ |

**空档期判定**：`[晚宴席.endDateTime, +10 分钟)` —— 抓包里 `endDateTime` 正是 06:00，
所以这段就是"凌晨六点到六点十分"。判定落在**组包之前**，**两顿都直接不发包**。
（**用户 2026-10-06 已确认：这 10 分钟两顿都不可吃**，见 §6.10。）

## 6.5 前后端分工（你拍板的双保险）
